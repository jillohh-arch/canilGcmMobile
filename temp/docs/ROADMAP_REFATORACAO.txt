================================================================================
ROADMAP DE REFATORAÇÃO — APP CANIL K9 GCM LIMEIRA
================================================================================

CONTEXTO:
- Projeto Flutter existente em produção (canil_gcm, v1.0.0+2)
- 6 parceiros da própria GCM Limeira usando ativamente
- Painel web React separado, acessa o mesmo Firestore diretamente
- Você (Jilles) controla tanto o app quanto o painel
- Arquitetura clean já parcialmente implementada (features/ + views/ legado)
- Stack: Provider, Firebase, Geolocator, fl_chart, pdf, local_auth

ESTE NÃO É UM ROADMAP DE CRIAÇÃO DO ZERO.
É um plano de refatoração gradual que:
- Mantém o app rodando pra parceiros sem downtime
- Aproveita o código que já funciona
- Migra visualmente pros mockups produzidos (01 a 13)
- Conclui a refatoração arquitetural inacabada (views/ → features/)
- Coordena evolução do schema Firestore com o painel React

PRINCÍPIO FUNDAMENTAL DA MIGRAÇÃO:
Toda mudança no schema Firestore precisa ser AVALIADA quanto ao impacto
no painel React. Mudanças seguras: adicionar campos novos. Mudanças
arriscadas: renomear ou remover campos existentes. Quando inevitável,
atualizar app + painel no mesmo deploy.

================================================================================
ESTRATÉGIA DE COORDENAÇÃO COM PAINEL REACT
================================================================================

Como você controla os dois, fica mais fácil. Mas precisa ter disciplina.

PRINCÍPIOS:

1. MUDANÇAS ADITIVAS NO SCHEMA SÃO SEGURAS
   Adicionar campo novo numa coleção existente não quebra o painel
   (ele simplesmente ignora). Use isso à vontade.

2. MUDANÇAS DE NOMEAÇÃO/REMOÇÃO PRECISAM SER COORDENADAS
   Se vai renomear campo X pra Y:
   a) Adiciona campo Y no Firestore mantendo X
   b) App grava nos dois (X e Y) por um tempo
   c) Painel React passa a ler Y
   d) Quando confirmado, app para de gravar X
   e) Depois, remove X do Firestore

3. NOVAS COLEÇÕES PODEM SER CRIADAS LIVREMENTE
   /dogs/{id}/commands não existe? Cria. Painel só usa quando estiver pronto.

4. NOMENCLATURA CONSISTENTE
   Definir: snake_case ou camelCase no Firestore?
   No app Dart, manter convenção snake_case nos campos do Firestore,
   converter pra camelCase nos models Dart.

WORKFLOW SUGERIDO:

A cada feature nova:
1. Definir schema Firestore (campos novos)
2. Criar models Dart correspondentes
3. Criar repositories
4. Implementar tela no app
5. Testar com Bono e Apolo no Firestore
6. Se painel React precisar exibir, planejar versão do painel
7. Comunicar parceiros sobre nova feature
